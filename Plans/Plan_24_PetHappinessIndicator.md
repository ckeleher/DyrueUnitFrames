# Plan 24 — Pet Happiness Indicator

**Status:** Not started.
**Created:** 15 August 2026
**Branch:** `Plan-24-pet-happiness-indicator`

---

## Request

> we need an indicator for hunter pet happiness levels

---

## Interpretation

An **icon on the pet frame** showing which of the three happiness levels the
pet is currently at. Not a bar, not a number, not a text readout.

Three things already exist and are worth naming up front, because they decide
most of the design:

1. **`Documents/SPEC.md` §3 already reserves this.** The `pet` row reads
   "Happiness indicator is TBC/Classic-specific." This plan *implements* a spec
   line rather than deviating from one, so no §5.7-style argument is needed.
2. **A `[happiness]` text tag already ships** (`Systems/Tags.lua:375`),
   rendering `Happy` / `Content` / `Unhappy` into any text element. So the ask
   is not "expose happiness at all" — it is "expose it as a *marker*, the way
   Blizzard's own pet frame does, rather than as a word competing with the
   name and health text for room on a 150×32 frame."
3. **`Compat.hasPetHappiness` already exists** (`Core/Compat.lua:134`), is
   already reported by `/duf compat`, and is **verified `true` on live Classic
   Era 1.15.9** (`COMPAT_FINDINGS.md:214`). The capability question is closed
   before this plan starts.

### Ambiguity, and the reading taken

"Hunter pet" is doing real work in the request and is taken literally. Warlock,
mage and other summoned pets have no happiness, and `GetPetHappiness()` is only
meaningful for a hunter's. The indicator must be **absent** on a voidwalker,
not present showing a stale or wrong face. Blizzard's own `PetFrame` gates on
the second return of `HasPetUI()` for exactly this reason, and this plan copies
that check. The existing `[happiness]` tag does **not** make this check — see
"Incidental fix" below.

**Own pet only.** `GetPetHappiness()` takes no unit argument; it answers about
your pet and nothing else. There is no API for another player's pet happiness,
so this is `pet` only and never `partypet1-4`. That is a hard API boundary, not
a scoping choice.

### The reading NOT taken

Happiness is *not* surfaced as a power bar. `Compat` already maps power type 4
to `HAPPINESS` and `Systems/Colors.lua:92` already has a color for it, but
that machinery is defensive — a hunter pet's *displayed* power is focus, and
`UnitPowerType("pet")` returns focus accordingly. Rendering happiness as a
second bar would mean fighting the power element to display a power the client
does not report as displayed. An icon is both what was asked for and what the
client actually supports.

## Design

### Where it belongs: a state in `Elements/Indicators.lua`

`Elements/Indicators.lua` is the Plan 1 state-marker row, and its header
comment states the intent plainly:

> the shape is a LIST rather than two hardcoded icons, so a third (PvP, leader,
> raid target) is a table entry rather than a rewrite.

This is that third. Adding a state buys, at zero cost: anchor target, point and
relative point, x/y offsets, growth direction, icon size, spacing, opacity, the
icon/square style toggle, the "only active states take a slot" packing rule,
and a complete options subtree generated by the loop at
`Config/Options_Layout.lua:1101`.

**Rejected: a `Elements/PetHappiness.lua` element of its own.** It would
duplicate every one of those settings for one icon, and add a tenth element to
the TOC and to every frame's build path. The only thing it would buy is an
independent screen position, which the existing `anchorTo` + point + offset
controls already provide.

### The shape problem, and the call

Happiness is **tri-state**, and `STATES` entries are **boolean** — each has an
`active(frame)` predicate and one fixed icon, with art applied in `Layout`
(config-time) and only position and visibility decided in `Update`
(per-refresh).

**Recommended: three boolean states — `happy`, `content`, `unhappy`.**

```lua
-- Elements/Indicators.lua, appended to STATES
{
    key = "happy", order = 3, label = L["Pet: happy"],
    requires = "hasPetHappiness",
    units = { pet = true },
    active = function(frame) return Compat.GetPetHappiness() == 3 end,
},
-- content (order 4, == 2), unhappy (order 5, == 1) follow identically
```

This needs **no change to `Build`, `Layout` or `Update` at all**. Each state
keeps one fixed art, so the Layout/Update split survives untouched; the three
are mutually exclusive so exactly one is ever active, taking exactly one slot;
and the generic options loop produces a per-level enable and tint for free.

That last point is a genuine feature rather than an accident: **"only mark the
pet when it is *not* happy"** is a real want, and it falls out as turning the
`happy` state off. A single tri-state entry could not express it.

**Rejected: one `happiness` state whose art is chosen per update.** It would
require moving `SetTexture`/`SetTexCoord` out of `Layout` and into `Update`,
breaking the split that the whole element is organised around, and it would
still need bespoke per-level color and enable controls that the three-entry
form gets from the existing loop.

### Two new fields on a state entry

The three-entry form needs the state table to carry gating, which it currently
has no notion of:

* **`requires = "hasPetHappiness"`** — names a `Compat` flag, exactly as
  `Units/Registry.lua:124` does for units. If a future client drops
  `GetPetHappiness` the way Cataclysm did, the states vanish rather than sit
  dead. Feature-probe, never version-check.
* **`units = { pet = true }`** — the state can only ever fire on these units.

Both are consumed in two places:

1. **`Elements/Indicators.lua`** — a state that fails either check is skipped
   in `Update` and never takes a slot. (`active()` returning false already
   achieves this; the fields make it declarative and, crucially, readable by
   the options builder.)
2. **`Config/Options_Layout.lua:1101`** — the loop skips such a state entirely
   for that unit, so three happiness headers do not appear on all eleven units'
   Indicators tabs. This is SPEC §FR-8.5's rule — *absent, not
   present-and-broken* — applied to a state rather than to a unit.

Add a matching `element.StateList(unitKey)` filter so the options builder asks
the element which states apply rather than reimplementing the predicate.

Note the precedent this quietly corrects: `resting` is player-only and handles
it today with a note reading "Resting is something the game only reports about
you, so this never shows on any other unit" (`Options_Layout.lua:1115`). One
dead control with an explanation is tolerable; **nine** dead controls (three
levels × three widgets) on ten units is not. `resting` should gain
`units = { player = true }` in the same change and shed its note.

### Reading the value: a `Compat` accessor

SPEC §5.5 makes `Core/Compat.lua` the only file permitted to call a
version-sensitive API. `GetPetHappiness` and `HasPetUI` are both such APIs, so:

```lua
--- Happiness of the player's pet, 1 (unhappy) to 3 (happy).
-- @return number|nil  nil when this client has no happiness, when there is no
--         pet, or when the pet is not a HUNTER pet -- a warlock's voidwalker
--         has no happiness and must not show a stale face.
function Compat.GetPetHappiness()
    if not Compat.hasPetHappiness then return nil end
    local hasUI, isHunterPet = false, false
    if _G.HasPetUI then
        local ok, a, b = pcall(_G.HasPetUI)
        if ok then hasUI, isHunterPet = a, b end
    end
    if not isHunterPet then return nil end
    local ok, happiness = pcall(_G.GetPetHappiness)
    if not ok then return nil end
    return happiness
end
```

`HasPetUI` is currently referenced nowhere in the codebase, so it needs a stub
in `Tests/wowstub.lua`.

### Art

Blizzard's happiness sheet, added to the `stateIcons` table at
`Core/Compat.lua:529` alongside the existing two — same reasoning, same blast
radius when a shared-code patch moves it:

| State | Texture | Tex coords (L, R, T, B) |
|---|---|---|
| `happy` | `Interface\PetPaperDollFrame\UI-PetHappiness` | `0, 0.1875, 0, 0.359375` |
| `content` | same | `0.1875, 0.375, 0, 0.359375` |
| `unhappy` | same | `0.375, 0.5625, 0, 0.359375` |

These are the coordinates Blizzard's own `PetFrame_Update` uses. Each cell is
24×23px, so the art is very slightly non-square; at the default 20px indicator
size the 1px stretch is invisible and not worth a per-state aspect override.

### Default tints — green / amber / red, not white

`resting` and `combat` both ship a white tint, because their art is
self-explanatory and white leaves it unmodified. **Happiness ships colored
tints instead**, and this is a deliberate departure:

* The three happiness faces differ only by **facial expression**. At a 20px
  indicator that is genuinely hard to read at a glance, which is the entire
  purpose of the row.
* Under `style = "square"` — Plan 1's fallback for when Blizzard art moves —
  white would render three *identical* white squares. Since only one shows at a
  time and they share a slot, the fallback would convey nothing at all. Colored
  tints keep the square style fully meaningful, which is what makes it a
  fallback rather than decoration.

Gentle tints rather than pure primaries, so the multiply against the art
preserves its detail: happy `(0.4, 1.0, 0.4)`, content `(1.0, 0.9, 0.4)`,
unhappy `(1.0, 0.4, 0.4)`. All three remain user-editable through the tint
control the options loop already generates.

### Events

Add `UNIT_HAPPINESS = true` to the element's static `events` table.
`Compat.RegisterUnitEvent` filters per-unit (SPEC §5.7), so only the pet frame
ever wakes for it, and `Compat.HasEvent` silently skips the registration
entirely on a client that lacks the event. `Elements/PowerBar.lua:23` already
registers it on the same terms, so this adds no new assumption.

The `element.GetEvents(frame, cfg)` hook exists (`Units/Factory.lua:429`, used
by `Elements/Text.lua`) and could register the event only when a happiness
state is enabled. **Not worth it here**: one rarely-firing unit-filtered event
on one frame does not justify making the element's event set dynamic.

### Incidental fix: the `[happiness]` tag

`Systems/Tags.lua:381` calls `GetPetHappiness()` directly, which is a small
SPEC §5.5 breach, and it checks only `UnitIsUnit(unit, "pet")` — so **it
currently returns a happiness string for a warlock's pet**. Repointing it at
`Compat.GetPetHappiness()` fixes both in one line and leaves exactly one
definition of "the happiness of a hunter pet" in the codebase, shared by the
tag and the indicator.

## Schema and migration

**The three `states.*` blocks are free.** They are new keys, so
`Defaults:EnsureProfile` fills them on load for every existing profile.
`Tests/tests.lua:641-653` already pins exactly this behaviour ("a key that did
not exist in the old schema … picks up the current default from
EnsureProfile"), including for `indicators` specifically.

**One key genuinely needs migrating.** `u.pet` does not set
`indicators = { enabled = true }`, so it inherits the schema default of
`false`. `EnsureProfile` only fills *absent* keys, so every existing profile
already has `pet.indicators.enabled = false` stored and would see nothing after
upgrading — the feature would ship invisible to precisely the hunters who asked
for it.

Recommended rule, in the existing `UNIT_RULES` idiom and scoped to the pet:

```lua
{
    path = { "indicators", "enabled" }, old = { false }, new = true,
    units = { pet = true },
    -- Only when the row is otherwise untouched. Someone who moved or resized
    -- it made a deliberate choice about a row they had turned OFF, and that
    -- choice outranks a new default.
    when = function(cfg)
        local i = cfg.indicators
        return i and i.x == 0 and i.y == 5 and i.size == 20 and i.growth == "RIGHT"
    end,
},
```

This mirrors the `background.enabled` rule, which already uses a `when`
predicate to separate an untouched default from a deliberate choice. **The
trade-off is real and worth stating**: a user who turned the pet's indicator
row off *without* otherwise touching it gets it back on. That is the residual
ambiguity the migration engine's whole "old values list" design accepts, and
one toggle undoes it.

`SCHEMA_VERSION` goes to 17. `COLLAPSED_THROUGH` stays at 11.

## Tests

Extend `testIndicators()` (`Tests/tests.lua:2529`) and add a pet-frame block.
`Tests/wowstub.lua:604` already stubs `GetPetHappiness` from `stub.petHappiness`,
so the fixture cost is just `HasPetUI`.

**Behaviour**

* Each of `stub.petHappiness = 3 / 2 / 1` shows exactly one of the three icons
  and hides the other two.
* The shown icon sits at slot one on the pet frame (resting is player-only and
  combat is off), using the existing `indicatorSlot` helper.
* Turning `happy` off shows nothing at happiness 3 but still shows `unhappy` at
  1 — the "only warn me when it's not happy" case, stated as a test because it
  is a design goal rather than a side effect.
* Happiness never occupies more than one slot: with pet combat also active,
  exactly two icons show.

**Gating** — these are the assertions that would catch the failure modes:

* `stub.isHunterPet = false` (warlock pet) with `petHappiness` still set → no
  icon. **And `[happiness]` returns nil**, which is the bug that exists today.
* `Compat.hasPetHappiness = false` → no happiness icon on any unit, and the
  three option headers are absent from the pet's Indicators tab. The Cataclysm
  case, and the reason `requires` exists.
* The three headers are absent from the **player and target** Indicators tabs
  and present on the **pet's** — the §FR-8.5 assertion.
* `resting`'s options are absent on the pet frame once it gains
  `units = { player = true }`, and its icon still never shows there.

**Defaults and migration**

* A profile at version 16 with an untouched pet indicator row comes out with
  `pet.indicators.enabled == true`.
* A profile at 16 whose pet row was **moved** (`y = -30`) comes out still
  `false` — the `when` guard. This is the test that keeps the migration honest.
* An ancient profile with `pet.indicators` absent entirely picks up the full
  current default including the three states.

**Gap this closes.** `testIndicators` only ever exercises the player frame, so
nothing today would catch a state that fires on the wrong unit. The per-unit
gating assertions above are the first coverage of that.

## Risks

| Risk | Handling |
|---|---|
| **`UNIT_HAPPINESS` may not fire on these clients.** No `COMPAT_FINDINGS` row asserts it does; presence has repeatedly turned out not to be function on this project (`UNIT_COMBO_POINTS`) | `Probe.lua:183` **already registers it**, so an existing probe run answers this at zero cost — do that before implementing and record the row. Even if it never fires, damage is bounded: `UNIT_PET` is in the pet's `changeEvents` and forces a whole-frame refresh, and happiness moves on a timescale of minutes. Worst case is a briefly stale face, not a wrong one |
| **Warlock/mage pet shows a happiness icon** | The `HasPetUI` hunter check, tested explicitly. This is the failure the request's word "hunter" is pointing at, and it is live in the `[happiness]` tag today |
| **Blizzard moves `UI-PetHappiness`** | Art lives in `Compat`'s `stateIcons` — one diff. `style = "square"` remains fully meaningful because the three tints differ, which is why they ship colored |
| **A future client drops happiness** | `requires = "hasPetHappiness"` removes the states and their options entirely. Feature-probe, never version-check |
| **Nine dead controls on ten unit tabs** | `units` gating, asserted by test. Fixes the pre-existing `resting` case in the same change |
| **The migration turns on a row someone deliberately turned off** | The `when` guard limits it to rows still at every shipped default. Stated in the release note; one toggle undoes it |

## Out of scope

`GetPetHappiness()` also returns **damage percentage** and **loyalty rate** as
its second and third values. Both are real hunter information and neither was
asked for. A tooltip on the happiness icon carrying "damage +/-X%, loyalty
level N" is the obvious follow-up; it wants its own request, since it needs a
tooltip anchor policy the indicator row has no notion of today.
